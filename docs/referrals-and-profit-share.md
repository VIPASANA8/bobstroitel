# Рефералы, учёт Cube и доля партнёра

Что реализовано и какие решения приняты явно. Код:
[`cash/referrals.py`](../cash/referrals.py),
[`cash/settlement.py`](../cash/settlement.py), атрибуция рейка — в
[`poker/engine.py`](../poker/engine.py) и [`cash/game.py`](../cash/game.py),
таблицы — в [`online/schema.py`](../online/schema.py), миграции
`20260907_0030` и `20260907_0031`.

## Три уровня учёта

| Уровень | Где живёт | Что хранит |
|---|---|---|
| 1. Игрок | `cube_rounds`, `hand_players.rake_micros` | Факт каждого раунда Cube (P&L игрока = `SUM(stake_micros - payout_micros)`) и доля рейка, удержанная с его денег в каждой раздаче. Отдельных таблиц нет: это запросы, а не сущности. |
| 2. Реферер | `referral_settlements` | Результат всей его группы за сутки, negative carryover, использованная база (high-water mark), начисление и его статус. |
| 3. Cube целиком | `partner_settlements` + `cube_adjustments` | Валовый Cube P&L за период, реферальные расходы, согласованные расходы, carryover партнёра, его доля. |

Уровни не смешиваются: расчёт уровня 2 читает факты уровня 1 (по Cube —
`cube_rounds`, по Poker — `hand_players.rake_micros`), расчёт уровня 3 читает
`cube_rounds` и уже закрытые расчёты уровня 2 по Cube.

## Реферальная привязка

* отдельная сущность `referral_codes` (код), не `acquisition_tenant_id`
  (тенант — это бренд и бот, а не источник трафика);
* `referrals.user_id` — первичный ключ, строка пишется один раз, `referrer_id`
  не обновляется нигде в коде: вторая ссылка возвращает первую привязку;
* привязка происходит **только при создании аккаунта**
  ([`online/auth.py`](../online/auth.py)) — иначе можно было бы «присвоить»
  уже играющего пользователя задним числом;
* запрещены: self-referral (`CHECK user_id <> referrer_id`), кольцо из двух
  аккаунтов (A→B→A), любая сторона с `users.internal = true`.

### Точки входа

| Ссылка | Что происходит |
|---|---|
| `t.me/<bot>?startapp=r<КОД>` | Mini App получает код в `start_param` внутри подписанной `initData`; привязка на первом входе. Основной путь. |
| `t.me/<bot>?start=r<КОД>` | Бот отвечает кнопкой «Открыть Poker8» с тем же `startapp`. Сам бот привязать ничего не может: аккаунта ещё нет. |

Слот `/start` уже занят nonce входа; коды и nonce различаются по длине
(9 символов против 32) и по префиксу `r`.

**Решение (п. 3 ТЗ):** 30-дневный период 15% отсчитывается от
`referrals.activated_at` — момента **первой завершённой real-money игры**, а не
от регистрации. Считается более ранняя из двух дат: первый раунд Cube и первая
завершённая раздача на CASH-столе. Поле заполняется расчётным проходом
(`_activate`, два UPDATE вместо `LEAST`, чтобы тот же код шёл и на SQLite).

## Cube: как считается результат

Для раунда результат проекта = `stake_micros - payout_micros`, где `payout` —
полная выплата игроку. Ставка 10, проигрыш → `+10`; ставка 10, выплата x6 →
`-50`. Это ровно то, что уже лежит в `cube_rounds`, отдельного пересчёта нет.

Игровая математика не тронута: RTP 80% живёт в вероятности
(`cash/cube.py: roll_face`), а не в коэффициенте, и `roll_face` не видит ни
рефералов, ни денег. Реферальный расход не может повлиять на вероятность.

## Расчёт реферального вознаграждения

Раз в сутки (UTC), по каждому рефереру:

1. собрать P&L проекта по всем его рефералам за сутки, с плюсами и минусами;
2. прибавить исторический `carryover` группы (он ≤ 0);
3. если итог ≤ 0 — выплата 0, итог переносится дальше;
4. если итог > 0 — он и есть база; она распределяется между **прибыльными**
   рефералами пропорционально их вкладу (largest remainder, до микро);
5. только затем к доле каждого применяется его ставка: 15% или 5%;
6. округление вниз, дробная часть микро остаётся у дома.

Реферал, перешедший с 15% на 5% в середине суток, входит в расчёт дважды —
раунды до границы и после — так что повышенная ставка не «протекает» дальше.

Carryover не обнуляется ничем: ни концом суток, ни концом месяца, ни
переходом 15% → 5%, ни неактивностью.

## Состояния начисления и hold

`pending` → `available` → (или) `reversed`.

* hold — **7 дней** (`POKER8_REFERRAL_HOLD_DAYS`), деньги лежат на клиринговом
  счёте `referral-pending` и на баланс не попадают;
* замороженный аккаунт (`cash_user_holds`) не получает релиз — начисление
  остаётся `pending` до решения оператора; это и есть fraud hold;
* `reversed` — возврат начисления внутри hold (chargeback, ошибка, фрод),
  проводка `referral_reversal`.

**Решение:** реверс возможен только пока начисление `pending`. После релиза
деньги могли быть отыграны или выведены, и возврат — это ручная операторская
корректировка с человеком за ней, а не действие джоба. При реверсе база
остаётся израсходованной: тот же день не может профинансировать второе
начисление. Это ошибка в сторону недоплаты — единственную сторону, где нельзя
создать деньги.

## Идемпотентность

* одна строка на `(referrer_id, source, period_start)` — уникальный ключ;
* один ключ ledger на строку: `referral / <источник>:<referrer>:<день>`,
  `referral / release:<id>`, `partner / <кадэнс>:<начало>`;
* повторный запуск, в том числе из двух процессов, ничего не доначисляет;
* день не рассчитывается, если у реферера уже есть расчёт за этот или более
  поздний день по этому же источнику — иначе цепочка carryover раздвоилась бы;
* «докуда посчитано» тоже отдельное на источник: проход, упавший после Cube,
  на следующем запуске всё ещё должен день по Poker.

Поэтому проход живёт на часовом housekeeping `CashWatchdog`, а не в отдельном
демоне: лишний запуск — no-op, пропущенный день подберётся следующим.

## Доля партнёра

```
валовый Cube P&L
− реферальные расходы Cube (начисления за дни периода, кроме reversed)
+ согласованные корректировки Cube (cube_adjustments, расход = отрицательный)
= чистая прибыль Cube
+ carryover партнёра (≤ 0)
→ если > 0: доля = итог × share_bps
```

* Poker в расчёт не входит вообще — источник только `cube_rounds`;
* доля — строка `partner_shares(effective_from, share_bps)`, а не константа;
  задать её на дату, попадающую в уже закрытый период, нельзя;
* минус месяца/недели переносится и не обнуляется;
* начисленное лежит на клиринговом счёте `partner-payable`; фактическая
  выплата партнёру — операторская операция, не задача джоба.

**Решение:** в БД пишутся **обе** кадэнсы — недели и месяцы, — но деньги
двигает только одна, `POKER8_PARTNER_PERIOD` (по умолчанию `month`). Вторая
считается по той же арифметике и служит отчётом. Две платящие кадэнсы делили
бы одну и ту же прибыль дважды.

Отсюда два следствия, о которых стоит помнить:

* корректировку Cube и новую долю партнёра запрещает только **оплаченный**
  (`posted`) период. Отчётная неделя внутри ещё не закрытого месяца ничего не
  запрещает — иначе месяц становился бы неисправимым со своей второй недели.
  Отчётные строки за такой период после корректировки остаются с прежними
  числами: они не пересчитываются;
* смену `POKER8_PARTNER_PERIOD` на живом проекте нельзя делать молча — прошлые
  строки другой кадэнсы уже записаны как неоплаченные и никогда не заплатят, а
  новая кадэнса начнёт свою цепочку carryover с нуля. Это отдельное решение с
  ручной сверкой, а не смена переменной окружения.

### Что относится к расходам Cube

Автоматически — только реферальные начисления, созданные Cube (`source='cube'`;
начисления с рейка Poker в расчёт партнёра не входят вообще).

Всё остальное вносится вручную как `cube_adjustments` с текстом причины и
именем оператора: комиссии платёжных провайдеров, относимые к Cube, кэшбэк
Cube, возвраты, chargeback, fraud loss, заранее согласованные корректировки.

Не относится к Cube и не может быть внесено без отдельного письменного
правила распределения: зарплаты, разработка, маркетинг, серверы, общие
административные расходы, любые расходы Poker.

**Решение:** аллокация комиссий провайдеров между Poker и Cube не
автоматизирована. Депозит не помечен «под Cube», честного правила разделения
нет, и автоматика здесь создала бы спор, а не решила его.

## Владельцы, партнёры, служебные аккаунты

`users.internal = true` (список `POKER8_INTERNAL_TELEGRAM_IDS`, синхронизируется
при старте). Такие аккаунты не могут быть ни реферером, ни рефералом, и
пропускаются расчётом. Это исключает двойную выплату: Referral RevShare плюс
Partner Profit Share с той же прибыли.

## Poker RevShare

База — **только фактически удержанный рейк**, отнесённый к деньгам конкретного
игрока. Проигрыш игрока другому игроку доходом проекта не является и в базу не
входит. Carryover для Poker не нужен и всегда нулевой: рейк не бывает
отрицательным, поэтому день Poker — это либо начисление, либо ноль.

Расчёт, ставки, распределение базы, hold, реверс и идемпотентность — те же,
что у Cube. Разными остаются источник и счёт: Poker финансирует начисления из
клиринга `table-rake`, Cube — из `cube-house`. Цепочки carryover раздельные
(`referral_settlements.source`), поэтому минус группы по Cube не съедает
вознаграждение с рейка, а рейк не закрывает минус Cube.

### Атрибуция рейка

Рейк раздачи — одно число (`state.rake`), и разложить его по игрокам задним
числом нельзя: `hands.result_json` хранит победителей и рейк пота, но не
контрибьюторов каждого слоя сайд-пота. Поэтому разбивка делается в момент
раздачи (`PokerEngine._charge_rake`), едет вместе с состоянием
(`state.rake_by_player`, сериализуется) и записывается при расчёте в
`hand_players.rake_micros`.

Метод — contributed rake, и он точен, а не эвристичен:

* **шоудаун**: в слое сайд-пота все вложили поровну (`own`), налог берётся с
  `pot.amount − own × len(winners)`, то есть ровно с доли проигравших → рейк
  слоя делится поровну между непобедившими контрибьюторами;
* **победа на фолде**: налог с `won − winner.total_invested` → делится
  пропорционально `total_invested` проигравших;
* остаток от деления — largest remainder, ties по id игрока, поэтому одна и та
  же раздача всегда делится одинаково;
* победитель никогда не платит рейк со своих денег, пот без борьбы бесплатен,
  до флопа рейка нет, потолок — 3 больших блайнда на раздачу.

Сумма разбивки обязана совпадать с `state.rake`: это проверяет и движок
(`assert`), и денежный инвариант в `cash/game.py::_settle` — при расхождении
раздача не рассчитывается, а стол встаёт на паузу, как при любом другом
нарушении escrow.

**Важно:** `hand_players.rake_micros` заполняется только для раздач, сыгранных
после миграции `20260907_0031`. Для более ранних он `NULL` (не ноль — это
разные утверждения), и Poker RevShare по ним не начисляется.

## Почему антифрод здесь скромный

Цифры, а не осторожность:

* Cube: RTP 80% → эдж проекта 20% оборота. Реферер получает 15% от прибыли,
  то есть при полном самореферале эффективный RTP = 80% + 0.15 × 20% = **83%**.
  Мультиаккаунт остаётся убыточным;
* Poker: прогнав рейк `R` между своими аккаунтами, абьюзер теряет `R` и
  получает обратно `0.15R`;
* расщепление плюсов и минусов по разным аккаунтам закрыто групповым
  carryover (уровень 2) — это и есть основная защита.

Опасной комбинация становится **только** вместе с withdrawable-бонусами
(депозитные, кэшбэк, рейкбэк, промокоды, задания). Сейчас их в проекте нет.
Правило на будущее: любой такой бонус обязан вычитаться из той же базы или
учитываться в совокупном экономическом эффекте до того, как будет включён.

## Инварианты и где они держатся

| Инвариант | Чем обеспечен |
|---|---|
| Нельзя выплатить больше доли от реально заработанного | база = групповой результат после carryover, ставка применяется после распределения |
| Убыток одного реферала нельзя спрятать | групповой расчёт, а не по-реферальный |
| Carryover не теряется | `carryover_after` каждой строки — вход следующей; смена суток/месяца/ставки его не трогает |
| Одни деньги не станут базой дважды | база израсходована в строке дня; повторный расчёт дня отклоняется |
| Poker не участвует в доле партнёра | источник расчёта — только `cube_rounds`, реферальный расход берётся с `source='cube'` |
| Poker и Cube не смешиваются | отдельные `source`, отдельные цепочки carryover, отдельные клиринговые счета фондирования |
| Доля рейка игрока объяснима | contributed rake, записывается в момент раздачи, сумма сверяется с `state.rake` |
| Доля партнёра — после referral cost и расходов | порядок в `_settle_partner_period` |
| Ledger сходится до микро | все проводки через `CashLedger` с балансом в ноль; тест на сумму всех счетов |
| Любое начисление имеет audit trail | строка расчёта + `breakdown_json` + типизированная проводка + `cash_audit_events` для операторских действий |
| Подозрительное можно задержать | заморозка аккаунта останавливает релиз, начисление остаётся `pending` |
| Игровая математика не изменилась | `cash/cube.py` не тронут |

## Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `POKER8_REFERRAL_HOLD_DAYS` | `7` | Сколько начисление лежит в `pending` |
| `POKER8_PARTNER_PERIOD` | `month` | Какая кадэнса реально платит партнёру |
| `POKER8_INTERNAL_TELEGRAM_IDS` | пусто | Владельцы/партнёры/служебные аккаунты |

Доля партнёра задаётся не переменной окружения, а строкой в БД:
`POST /api/cash-admin/partner/share`.
